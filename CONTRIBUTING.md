# Contributing to Mojibake

This document provides guidelines and information for contributors.

## Building from source

Some .h/.c/.ts files are automatically generated by the build scripts from Unicode standard files.
If you make changes to these files, they will likely be rewritten when `make generate` is run. If
you see "This file/enum/function is automatically generated. Do not edit", don't do it.

1. `src/unicode-data.h` file
2. `src/api/mojibake.d.ts` file
3. `src/api/locales.ts` file
4. `src/rust/mojibake-sys/src/functions.rs` file
5. `tests/example.c` and `tests/ext/cpp/example.cpp` files
6. `API.md` file
7. `src/mojibake.h` functions list
8. `src/unicode.h` and `src/api/unicode.ts` enumerations
9. `src/locales.h` enumeration and `src/locales.c` tables
10. `src/properties.c` tables
11. `mjb_bidi_brackets` and `mjb_bidi_mirroring` arrays in `src/bidi.c`
12. `src/CMakeLists.txt` source list

Public function declarations, their documentation, and the C and C++ examples come from
`utils/generate/functions.ts`. Edit that file and run `make generate` instead of editing the
outputs.

### Requirements

Mojibake requires a C11 compiler. Building the C sources as C++ requires C++17, and the
header-only C++ wrapper requires C++20 with concepts and `<ranges>`. The minimum supported compiler
versions for the library are:

| Toolchain | Minimum version | Language modes |
| --- | --- | --- |
| GCC | 9 | C11 and C++17 |
| LLVM Clang | 10 | C11 and C++17 |
| Apple Clang | 16 | C11 and C++17 |
| MSVC | 19.30 (Visual Studio 2022) | C11 and C++17 |

CI builds and smoke-tests both language modes with the exact GCC 9 and LLVM Clang 10 baselines.
Those compilers lack C++20 support, so the test suite skips the C++ wrapper tests there. A C++
job runs them only when its compiler passes the C++20 check in `tests/CMakeLists.txt` (GCC 10 and
later do; Clang 14 with libstdc++ does not).
The macOS and Windows jobs continuously test the supported Apple Clang and MSVC families using the
hosted platform toolchains. MinGW-w64 and Emscripten are also tested as rolling compatibility
targets.

On POSIX systems: Linux, macOS, FreeBSD, OpenBSD, NetBSD, Haiku:

- `CMake` 3.14 or newer
- `Node.js` and `npm`
- `make` (usually already included in the release)
- `curl` and `unzip` (usually already included in the release)

On Windows 10/11:

- The MSVC compiler. [Build Tools for Visual Studio](https://visualstudio.microsoft.com/downloads/#build-tools-for-visual-studio-2026) is enough
- `CMake` 3.14 or newer
- `Node.js` and `npm`

### POSIX

At the very first run:

```sh
cd utils/generate
npm ci
```

Then from root folder:

```sh
make
make test
```

### Windows

At the very first run, from a [Visual Studio developer command prompt](https://learn.microsoft.com/en-us/visualstudio/ide/reference/command-prompt-powershell?view=visualstudio):

```powershell
cd .\utils\generate
npm ci
```

Then from root folder:

```powershell
nmake /F Makefile.nmake
nmake /F Makefile.nmake test
```

## WebAssembly

To build the WASM module you need [Emscripten](https://emscripten.org) and generate assets with:

```sh
make wasm
```

or:

```powershell
nmake /F Makefile.nmake wasm
```

This builds the module in `build-wasm/`, copies `mojibake.js` and `mojibake.wasm` into
`src/api/`, and regenerates the demo site in `src/site/`. Use `make build-api` to also build the
TypeScript package.

You can run a local server with:

```sh
make watch-site
# Open http://localhost:6251
```

Run the JavaScript API server with:

```sh
make watch-api
```

## Code Style

- We follow a consistent code style using clang-format
- Use 4 spaces for indentation (no tabs)
- Maximum line length is 100 characters
- See .clang-format for complete style configuration
- `make lint` checks formatting (it uses Apple's `xcrun clang-format`, so it is macOS-only; on other
  platforms run `clang-format --dry-run --Werror` directly)
- `make tidy` runs clang-tidy with `.clang-tidy`; set `CLANG_TIDY` to select a specific binary
- Record user-visible changes under `[Unreleased]` in `CHANGELOG.md`

## Developer Certificate of Origin

By contributing to Mojibake, you certify that your contribution complies with the
[Developer Certificate of Origin 1.1](DCO).

Sign off every commit with your real name and email address:

```sh
git commit --signoff
```

This adds a trailer to the commit message:

```text
Signed-off-by: Your Name <your.email@example.com>
```

The sign-off must match the commit author's name and email address. It certifies the contribution;
it is not the same as cryptographically signing a commit with `git commit -S`.

## Pull Request Process

1. Fork the repository and create a new branch for your feature/fix
2. Write clear commit messages explaining your changes
3. Sign off every commit as described above
4. Add/update tests to cover your changes
5. Ensure all tests pass before submitting
6. Submit a pull request with a description of your changes

## Testing

You can run tests in multiple ways. On POSIX platforms:

1. `make test` run tests compiled as C (pass a name filter with `make test ARGS="-f normalization"`)
2. `make test-cpp` run tests as C++
3. `make test-release` / `make test-cpp-release` run optimized C or C++ builds
4. `make test-asan` run tests with [AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html)
5. `make test-ubsan` run tests with [UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)
6. `make test-no-names`, `make test-no-collation`, `make test-no-idna`, `make test-no-security`
   run tests with one optional feature disabled
7. `make test-minimal` / `make test-cpp-minimal` run C or C++ tests with every optional feature
   disabled
8. `make ctest` run tests using [ctest](https://cmake.org/cmake/help/latest/manual/ctest.1.html),
   including the CLI output checks
9. `make ctest-cpp` run C and C++ tests using `ctest`
10. `make test-wasm` rebuild the WASM module with Emscripten, build the TypeScript package, and
    test the WASM API in Node and a local Chromium-based browser (set `MJB_BROWSER` if it is not on
    the default search path)
11. `make test-rust` run rustfmt, clippy, and the Rust crates' tests

Groups of the targets above:

- `make test-native` runs `test` and `test-cpp`
- `make test-optimized` runs `test-release` and `test-cpp-release`
- `make test-features` runs every feature-disabled configuration
- `make test-sanitizers` runs `test-asan` and `test-ubsan`
- `make test-all` runs all of the local native configurations

Windows 10/11 (`Makefile.nmake` provides the same targets):

1. `nmake /F Makefile.nmake test` run tests compiled as C
2. `nmake /F Makefile.nmake test-cpp` run tests compiled as C++
3. `nmake /F Makefile.nmake test-asan` run tests with `AddressSanitizer`
4. `nmake /F Makefile.nmake test-ubsan` run tests with `UndefinedBehaviorSanitizer`
5. `nmake /F Makefile.nmake ctest` run tests using `ctest`
6. `nmake /F Makefile.nmake ctest-cpp` run C and C++ tests using `ctest`

Docker:

1. `make test-docker` run tests on Alpine Linux, using Docker
2. `FUZZ_TIME=60 make fuzz` fuzz the public API with libFuzzer, using Docker

Running the test binary by hand:

The tests read the Unicode data files under `unicode-data/` with paths relative
to the repository root, so at startup `mojibake-test` changes into that directory. It is resolved
in this order: the `MJB_TEST_SOURCE_DIR` environment variable if set and non-empty, then the
repository root recorded at build time by `tests/CMakeLists.txt`, then the current directory.

```sh
MJB_TEST_SOURCE_DIR=/path/to/mojibake /path/to/build-test/tests/mojibake-test -f normalization
```

Important information about testing when adding new code:

- We "assert" something that is true, not something that is false
- Add unit tests for any new functionality
- Run the full test suite before submitting changes
- Current test coverage is tracked in `TESTS.md`; regenerate it with `make coverage`
- Aim to maintain or improve test coverage
- Never remove a test, always add one

We use Attractor to run tests. Define a test case with `ATT_TEST(name) { ... }`. A new test file
must be added to `TEST_SOURCES` in `tests/CMakeLists.txt`.

```c
ATT_ASSERT(what_you_are_testing, expected_value, "Description");
```

Use `ATT_ASSERT_STATUS` for `mjb_status` values.

For example, imagine we have found a bug in the `mjb_codepoint_count` function that does not
correctly count the codepoints in the `"Hello, test"` string and we fixed it. In `tests/encoding.c`,
add a new assertion:

```c
size_t count = 0;
mjb_text text = mjb_text_utf8("Hello, test", 11);
ATT_ASSERT_STATUS(mjb_codepoint_count(&text, MJB_MALFORMED_STOP, &count, NULL), MJB_STATUS_OK,
    "UTF-8 Hello, test status");
ATT_ASSERT(count, (size_t)11, "UTF-8 Hello, test");
```

Then run `make test` and `make test-cpp` to be sure all tests are working.

## Rust crates

The Rust crates live in `src/rust/`; their user-facing documentation is
[src/rust/README.md](src/rust/README.md).

### Building and testing

From the repository root:

```sh
make test-rust
```

This runs rustfmt, clippy, and the tests with all features on and with all features off.

The `mojibake-sys` build script looks for the C sources in this order:

1. `MOJIBAKE_SRC_DIR`, when it is set
2. the repository's `src/` directory, when the crate is built inside a Mojibake checkout
3. `mojibake-sys/csrc/`, the git-ignored copy that `make vendor-rust` makes for packaging

A checkout wins over `csrc/`, so a leftover copy is never compiled in-tree. The source list comes
from the generated `SOURCES` block of `CMakeLists.txt`.

The declarations in `mojibake-sys/src/functions.rs` are generated from
`utils/generate/functions.ts` by `make generate`; do not edit them. The types, constants, and
layout tests in `mojibake-sys/src/lib.rs` and `mojibake-sys/shim/layout.c` are written by hand.

### Packaging and publishing

`make package-rust` copies `src/*.c`, `src/*.h`, `src/CMakeLists.txt`, and `LICENSE` into
`mojibake-sys/csrc/`, then runs `cargo package --workspace` and
`cargo publish --workspace --dry-run`. Both crates are packaged and each is built from its
`.crate` file, with `mojibake-rs` resolving the unpublished `mojibake-sys` from Cargo's local
staging registry. CI runs it on every push. It needs Cargo 1.90 or newer for workspace packaging;
users of the crates still need only Rust 1.77.

Cargo treats the git-ignored `csrc/` as uncommitted, so the target always passes `--allow-dirty`
and instead refuses to run when `src/` or `LICENSE` has uncommitted or untracked changes. Set
`ALLOW_DIRTY=1` to package a work in progress. Extra Cargo flags go in `ARGS`.

To release the crates:

1. Set `VERSION` and run `make update-version`. It sets the workspace version in `Cargo.toml`,
   the `mojibake-sys` dependency of `mojibake-rs`, and both entries in `Cargo.lock`.
2. Commit the release and check that `make test-rust` and `make package-rust` pass.
3. Publish from the same clean checkout. Cargo uploads `mojibake-sys` first, then `mojibake-rs`:

   ```sh
   make vendor-rust
   (cd src/rust && cargo publish --workspace --locked --allow-dirty)
   ```
